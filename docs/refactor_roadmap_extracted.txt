
    Refactor Roadmap for AI-Portfolio’s Agentic Analytics Integration
    
    Runtime Refactor Goals and Architecture
    Unify agentic execution for all flows: The primary goal is to run all analytics workflows (fresh runs and revisions, single-agent and multi-agent) on the OpenAI Agent SDK, eliminating the split between deterministic pipelines and agent-based controllers[1]. This “agent everywhere” approach ensures consistent session memory usage, telemetry events, and UI evidence across flows[2].
    Preserve deterministic direct mode: We will leave the FlowMode.DIRECT pipeline untouched. The existing planner-executor sequence (SQL → chart → accessory → analysis) remains in place for “instant answer” scenarios requiring predictable, low-latency outputs[3]. By not altering PlannerExecutorFlow.events() for direct mode, we maintain cache-independent fresh answers as described in the current architecture[4]. All refactor work will target the revision and multi-agent paths, ensuring direct flows continue to function exactly as before.
    Adopt the supervisor + specialists pattern: For multi-agent workflows, we will implement the “supervisor agent with specialists-as-tools” model recommended in the design docs[5]. In this architecture, a single Supervisor agent uses the Agent SDK to call domain-specific specialist tools (for SQL generation, charting, web retrieval, analysis, etc.) rather than orchestrating via custom Python logic. This mirrors the current MultiAgentFlow design (supervisor delegating to specialists) while leveraging the Agent SDK’s built-in orchestration patterns[6]. It avoids complex agent handoffs initially, keeping one continuous agent run and a unified timeline of steps in telemetry. After this is stable, we can consider more advanced orchestration (e.g. a planner agent coordinating multiple agents) as a future enhancement, but the initial refactor will stick to the simpler supervisor-as-tool-caller approach[7].
    Agent runtime as the common engine: Both single-agent and supervisor flows will converge on using the same Agent SDK Runner/AgentRuntime with different configurations. We will define distinct instruction sets for a fresh run vs. a revision run, effectively creating something like a FreshRunPlannerAgent versus a RevisionPlannerAgent within the existing AgentRuntimeConfig framework[8]. The fresh-run agent will be instructed to always execute the full sequence of tools (SQL → chart → accessories → analysis), while the revision agent will load cached artifacts (via SessionStateSnapshot) and only re-run the necessary steps based on the revision directive[8]. Both will use the same set of tool primitives to ensure consistency. This design preserves the “single source of truth” business logic: the underlying behaviors (SQL planning, execution, chart generation, narrative synthesis) remain governed by the current planner code, just invoked through the Agent SDK interface rather than via bespoke controllers[9].
    Reuse existing planner logic via tools: To minimize risk and avoid a ground-up rewrite, we will wrap the existing lane functions as Agent SDK tools[10]. For example, functions like planner.sql_lane.stream_sql_lane, planner.stream_chart_lane, planner.stream_analysis_lane (and their accessory fan-out logic) will each be exposed to the agent as callable tools. Each tool wrapper will invoke the current generator/adapter, stream results as it does today, and use hooks to record the output in the session state or receipts cache (replacing what the planner sequencer does)[11]. This way, the agent’s “tool use” produces the same artifacts and SSE events we have now, but under the unified AgentRuntime. The benefit is that fresh and revision flows share one implementation of each step, and when we eventually retire the deterministic code path outside direct mode, we won’t have duplicate logic.
    Pinned model and guardrails: All agent-based flows will standardize on OpenAI GPT-5 as the model backbone. In particular, we will mandate use of the gpt-5-mini-2025-08-07 model (or an equivalent GPT-5 engine) for every Agent SDK execution, to ensure uniform capabilities and avoid regressions[12]. This model is already recommended in our development guidelines and provides the needed function-calling and multi-turn reasoning support. Additionally, we’ll incorporate our existing guardrails into the Agent SDK configuration – for example, the follow-up classifier logic, stock-answer short-circuit conditions, and latency safeguards will be implemented as Agent SDK guardrails or callbacks rather than ad-hoc Python checks[13]. This integration will let us eventually remove those external helpers while maintaining their effect (e.g. an inappropriate follow-up can trigger an Agent “end run” or a tool omission via guardrail verdict). The overall architecture after refactoring will have a single agent runtime pipeline for non-direct modes, improving maintainability and aligning with OpenAI’s best-practice patterns for tool-using agents.
    
    
    Backend Refactor Steps (by File/Module)
    Introduce tool wrappers for planner lanes: Create a new module (e.g. backend/analytics/flows/pipeline_tools.py or expand pipeline_tools if existing) to define Agent SDK Tool classes or functions that wrap each major lane:
    SQL Tool: Wraps flows/planner/sql_lane.stream_sql_lane – the tool’s call will execute the SQL planning &amp; execution, yield the same sql_ready events, and store the resulting SQL and data in the session state.
    Chart Tool: Wraps planner/stream_chart_lane – executes chart spec generation and yields chart_ready (or patches) events.
    Analysis Tool: Wraps planner/stream_analysis_lane – runs the narrative LLM generation and yields analysis_ready or similar events.
    Accessory Tools: For any parallel accessories (market data, web search), wrap the fan-out initiation (fanout.start_tool_parallelism) or the specific adapter calls. They should stream stock_ready/web_ready events as currently done in derive_accessory_events[14]. Each wrapper should be a thin shim that calls the underlying function/generator and captures its outputs (by invoking our persistence hooks like _persist_session_state or SessionStateSnapshot.record_outputs()). No business logic changes are made inside these tools – they merely expose our existing pipeline stages to the Agent SDK so the agent can invoke them in order[10]. All new tool definitions will be registered with the agent’s tool registry (likely via an extension of the current PlannerToolRegistry mechanism).
    Extend AgentRuntime configuration for dual modes: Update backend/analytics/agent_orchestrator/AgentRuntimeConfig (or analogous config class) to support two distinct Planner Agent personas:
    FreshRunPlannerAgent: Always calls the full sequence of tools (SQL, Chart, etc.) regardless of cache state. This agent’s prompt/instructions will reflect the deterministic contract (e.g. “Always produce a new answer by executing all steps, even if cached data exists”) to mimic the planner-executor behavior[15].
    RevisionPlannerAgent: Loads existing artifacts from SessionStateSnapshot and only calls the tools necessary for the user’s revision request. Its instructions will be like “Only refresh the parts of the analysis that are outdated or specifically requested, using cached results for everything else,” aligning with how revisions currently work[15]. We will implement these as separate configuration presets or subclasses, living alongside the existing AgentRuntimeConfig. This likely involves defining different prompt templates or agent “roles” in the Agent SDK initialization, but reusing the same underlying Runner.run_streamed logic. We will also incorporate the guardrail hooks here (for follow-up classification, etc.), so that if (for example) the classifier indicates a “stock-only update,” the agent can decide to skip tools or exit early (this could be done by injecting a guardrail that stops the run or by the agent’s logic reading a flag)[13].
    Shim controller logic to AgentRuntime: Modify the flow controllers so that for all non-direct modes, the AgentRuntime takes over execution:
    In backend/analytics/flows/planner_executor.py (which currently houses the PlannerExecutorFlow for deterministic runs), add a check in the events() method: if the FlowMode is SINGLE_AGENT or MULTI_AGENT, then do not run the usual sequential planner. Instead, initialize an AgentRuntime with the appropriate config (fresh or revision as decided above) and call its run_streamed() method. We can pass in the prepared PlannerToolRegistry (which now contains our new tool wrappers) so the agent knows what tools it can use[16]. Essentially, PlannerExecutorFlow.events() becomes a shim – for direct mode it does what it always did, for agentic modes it delegates to the Agent SDK.
    Ensure the existing SingleAgent and MultiAgent controller classes use this new pathway. For example, SingleAgentController (defined in flows/single_agent_tools.py) can likely be simplified or even replaced. Instead of orchestrating tools manually, it should call into the modified PlannerExecutorFlow or directly instantiate the agent runtime. Its role reduces to preparing any specific context (like setting up the AgentMemory with cached state via AgentMemory.load_plan_state() – which is already done for revisions today[17]) and then yielding the events coming from AgentsStreamBridge. We will aim to deprecate SingleAgentController as a distinct execution path; after refactor, it may just wrap the new unified pipeline or become an alias for invoking the Agent runner.
    Similarly, update MultiAgentFlow (in flows/multi_agent.py) to use the Agent SDK. Currently, MultiAgentFlow coordinates specialists but still leans on PlannerExecutorFlow for core logic[18]. After refactor, MultiAgentFlow will initialize a Supervisor agent (with a similar config to FreshRunPlannerAgent but capable of spawning tool calls to specialists) and again call AgentRuntime.run_streamed(). The difference from single-agent mode is that the Supervisor agent’s tool list will include not only the basic lane tools but also possibly specialized tools or prompt instructions to label the tasks. However, if we follow the supervisor-as-tools approach, we may treat each specialist skill as just another tool (the specialist’s “action” is the tool’s logic). In practice, this might mean the same set of tools can be used; the distinction is mainly in how the agent instructions are written (the Supervisor agent decides which subset of tools to call for each topic/task). We will register tools like “Chart Specialist Tool” that maybe only produce a chart if called, etc., reusing the underlying lane but allowing the agent to attribute it to a specialist.
    Remove any now-redundant branching in these controllers. For instance, if SingleAgentController had logic to handle revision vs fresh differently, that can go away because the AgentRuntime config will handle it. If MultiAgentFlow had custom code for assembling a plan or merging results from specialists, much of that can likely be removed in favor of letting the Agent SDK manage parallel tool calls or sequential tool invocation. The refactored controllers become thin orchestrators that start an agent run and stream back its output.
    Consolidate artifact handling and receipts: Ensure that the session artifact caching and receipts generation works identically through the new agent path. The current system uses ToolInvocationReceipt objects and SessionStateSnapshot to record outputs from each stage for use in revisions and follow-ups[1][19]. In the new flow, as each tool finishes, we will invoke the same hooks (e.g., SessionStateSnapshot.record_outputs or a new unified mechanism) to capture the result. The Agent SDK’s session support will help here – we can attach the session state so that it persists between runs, making a fresh agent run produce a state that a subsequent revision agent can consume[19]. This step may involve minor changes to AgentMemory or how AgentRuntime is invoked (to ensure it uses an existing session ID for revisions). The goal is that after a fresh run via the Agent, the cached artifacts and receipts are indistinguishable from those produced by the legacy deterministic run. This guarantees that follow-up queries, revisions, and UI displays (e.g. showing which artifacts were reused) continue to work with no regression.
    Remove legacy planner and runtime logic: With the above changes in place, we will eliminate the obsolete code paths and controllers:
    Legacy AnalyticsWorkflow class: The old monolithic AnalyticsWorkflow (in backend/analytics_agent.py) and its deterministic helper methods for SQL, chart, and narrative generation will be retired. These include methods like _build_market_share_sql, _build_margins_sql, _build_growth_sql for constructing SQL queries, and _build_echarts_spec for chart specs[20][21]. They were part of the earlier pipeline for constructing outputs but are now superseded by the Planner/Agent tooling. Any unique logic in these helpers (if still needed) should be ported into the current planner or tool templates, then the helpers can be deleted. This cleans up code and avoids maintaining two ways to generate charts or SQL.
    SingleAgentController and MultiAgentFlow: Once the AgentRuntime is fully handling single and multi-agent flows, these classes’ custom implementations (in single_agent_tools.py and multi_agent.py) can be largely removed or reduced to stubs. We will strip out methods that attempted to coordinate tools outside the Agent SDK (such as _stream_agentic_lane_selection, _derive_tasks, _planner_agent etc., which were workarounds to simulate agent planning in code)[22][23]. After refactor, the actual planning and task delegation happens inside the Agent’s reasoning loop instead of these Python functions, so we can delete them. We will keep any utility functions that are still generally useful (e.g., some normalization or identifier generation helpers) only if the new system calls for them.
    Planner executor fallback logic: Any conditional code that checks flags like AGENTIC_REVISIONS_ENABLED to decide between agent vs planner execution will be updated. If the vision is to eventually run everything on the Agent SDK, we might remove such toggles or invert them (the default path becomes agent, and perhaps a dev-only flag could revert to legacy if needed for debugging). The architecture already emphasizes “no legacy fallbacks” – meaning once we switch over, users won’t hit the sequential pipeline at all[24]. So, we plan to delete the legacy pipeline code that is not used in direct mode. This includes old revision pathways that aren’t agent-based and any special-case branches in PlannerExecutorFlow or other pipeline code for non-agent operation.
    Deprecated utilities: The follow-up classification logic (FollowUpClassifier in analytics/routing/) and revision directive utilities will be reevaluated. In the refactor, the follow-up routing should be encapsulated by agent guardrails or by the agent deciding whether to do a full run or a partial run based on session context. As that gets integrated, the FollowUpClassifier.classify() method and related heuristic code can likely be removed or drastically simplified[25]. We will verify that the agent’s decisions replicate the classifier’s outcomes (stock answer vs full refresh) and then retire the classifier module. Similarly, any “regression-only” pathways – for example, if we had code that only runs in tests to compare agent vs planner outputs – will be removed once tests are updated to directly validate the agent outputs (see Testing Guidelines below). By the end of the refactor, the backend codebase should have a single unified runtime path for analytics flows (plus the preserved direct mode), with no dead code or outdated branches lingering.
    Backend module-by-module checklist: In summary, the files and modules affected and actions to take:
    backend/analytics/flows/planner_executor.py: Keep direct flow logic, add agent-runtime delegation for other modes, remove any outdated revision handling in this class.
    backend/analytics/flows/single_agent_tools.py: Remove or simplify SingleAgentController and related functions that won’t be needed (lane decision tools, etc.), possibly relocate any needed pieces to a more generic place if still used by agent runtime.
    backend/analytics/flows/multi_agent.py: Strip out manual specialist coordination functions. Rewire MultiAgentFlow to start the Supervisor agent. Remove the internal “planner agent” concept if present, since the SDK agent will handle planning.
    backend/analytics/agent_orchestrator/agent_runtime.py and config classes: Add support for new instruction sets, ensure AgentsStreamBridge integration (subscribing to run_step events) covers fresh runs as well[2].
    backend/analytics_agent.py: Deprecate the AnalyticsWorkflow class and its _build_* helper methods[26][21]. If any part of this file is still used for initialization, see if it can be cleanly removed in favor of the flows package.
    backend/analytics/routing/follow_up_classifier.py: Plan to remove after verifying agent guardrail replacement. In interim, perhaps leave it but mark as deprecated.
    backend/tests/...: Many tests will need updates (addressed later), but note we expect to delete any test utilities that spin up the old pipeline exclusively for comparison. Tests should run the new agent path or direct path only.
    
    
    Frontend Stream &amp; UI Alignment Steps
    Unify SSE event handling: Update the frontend analytics stream hook (components/analytics/hooks/useAnalyticsMemoryStream.ts) to handle the Agent SDK telemetry events for all flows. Currently, the UI expects certain SSE event types only during revision (e.g., agent_coordination, agent_tool_call, web_topics_pending, etc.) and uses simpler events for fresh runs[27]. After the refactor, fresh runs will also produce rich agent telemetry via AgentsStreamBridge (like tool_call_delta, tool_call_summary, reasoning steps, etc.), so the front-end stream logic must listen for those events in every mode except direct. We will ensure the SSE payload structure is consistent: each agent tool invocation and reasoning chunk will come through as an event that the UI can interpret. The hook should accumulate ProcessStep entries from these events, building a timeline of the agent’s thought process and tool actions instead of the fixed pipeline steps. Essentially, the same client-side logic used to display revision flows will now be applied to fresh flows in single-agent/supervisor mode, yielding a unified experience.
    ProcessPanel timeline enhancements: The ProcessPanel component will continue to show a step-by-step breakdown of the analytics process, but we’ll align it with the new telemetry:
    Ensure that agent reasoning steps (the agent’s internal thoughts or plan outputs) are displayed as descriptive entries. The Agent SDK emits reasoning deltas (e.g., through response.reasoning_text.delta events that we convert to agent_reasoning SSE messages). We’ll surface those so the user can see the AI’s chain-of-thought (making the UI “UI-as-chat” style, where the agent’s thought process is visible)[17].
    Display tool usage steps with clear labels. Each time the agent calls a tool, AgentsStreamBridge emits tool_call_delta and a final tool_completion event with metadata including a tool_call_id and tool name[28][29]. The ProcessPanel will be updated to create a new entry for the tool invocation (e.g., “Chart Specialist tool is running…” perhaps with a spinner, then “Chart Specialist tool completed”). We will use the tool metadata to label these steps. For example, if the tool name is “chart_generation”, the UI can display “🛠️ Chart Generation tool invoked”. For multi-agent (supervisor) flows, we might prepend the specialist role: e.g., “Chart Specialist: Chart Generation tool invoked” – or use the specialist’s name from metadata.
    Specialist attribution: In multi-agent scenarios, multiple specialized tools will be called in one session. The UI already has a concept of SpecialistCard entries and specialist-related metadata in the process view[30][31]. We will leverage the agent_supervisor_started and summary events (which list all specialists engaged) to annotate the timeline. For instance, we can label a block of steps with the specialist agent’s name or icon. The design doc suggests simply tagging the card headers with the specialist name using the tool_call_id or agent identifier[5]. Concretely, when a tool_call_summary comes in for a tool executed by a specialist, we can update the corresponding ProcessPanel entry’s header to include “(Chart Specialist)” or similar, so it’s clear which sub-agent handled that part. This preserves the “fan-out” visualization: although the ProcessPanel is a single combined timeline, each step is marked by which specialist produced it.
    WorkflowCanvas and fan-out visualization: The WorkflowCanvas (and SingleAgentFanoutCanvas) components provide a visual diagram of the analytics workflow. We need to ensure these remain useful and reflective of the new execution:
    For single-agent flows, the process is linear (the agent deciding sequence), so the canvas might simply show a linear flow of steps. We may not need a complex graph, but we can reuse the existing visualization for tool stages. If currently the canvas for single-agent mode shows multiple tools branching (perhaps it doesn’t, given the name “FanoutCanvas” suggests it might for parallel tasks), we’ll adjust it to highlight any parallel accessory retrievals (stock vs web) as branches. The agent, when it triggers fan-out, will effectively call a function that runs multiple adapters concurrently (we’ll still get separate SSE events for each accessory). The canvas can represent those as parallel nodes (as it likely does now for direct mode fan-out of web vs stock).
    For multi-agent (supervisor) flows, if we maintain the simple supervisor-as-tool model, from the UI’s perspective it may look similar to single-agent (since one agent orchestrates everything). However, the canvas can still depict the involvement of specialists. For example, it could show the Supervisor agent at top and multiple specialist nodes (SQL, Chart, Analysis specialists) branching off. As the run proceeds, we could highlight which specialist is active. Given the question’s emphasis, we won’t radically change the UI layout – just ensure it aligns with the telemetry. If the Agent SDK produces a nested structure (e.g., a specialist agent run within the supervisor’s run), we might consider representing nested boxes or an expandable timeline in the future[7]. For now, the plan is to retain the current visual breakdown (e.g., showing that multiple agents or tools were involved) using the data we have. The ProcessPanel plus LiveArtifacts together already show most of this (timeline + artifacts per lane), so the canvas just needs to complement it with an overview.
    We will test these visualizations with the new data. The expectation is that because we’re translating Agent SDK events to the same SSE schema we used before (just more consistently), the existing canvas logic will largely continue to work. Minor tweaks might include adding support for new event types or ensuring that when an agent finishes, the canvas marks all steps complete.
    LiveArtifacts component updates: The LiveArtifacts panel (which shows final outputs like the chart, data table, and narrative) will be updated to reflect agent attribution and maintain clarity:
    Badges for artifact origin: We will introduce labels or badges on each artifact indicating if it was generated or reused and by which part of the agent. For example, if the chart was produced by the Chart Specialist agent, we might show a small caption “Produced by Chart Specialist” near the chart card. If an artifact was cached (reused from a prior run), the UI already has a notion of reuse badges (e.g., a lane reuse notice) – we can continue to display “(reused)” and perhaps also attribute which agent originally created it if meaningful. The telemetry provides enough info (specialist names, and whether an event was reused) to do this[32][33]. We want the user to easily grasp, for example, that “the SQL step was skipped (reused) but the Analysis was freshly regenerated by the Analyst agent.”
    Consistent formatting by mode: We’ll ensure the styling and headings in LiveArtifacts correspond to the flow mode. The component already defines different labels for Planner-Executor vs Single-Agent vs Multi-Agent modes (e.g., “Planner-Executor Flow” vs “Single-Agent Flow” badges)[34][35]. We may adjust the wording slightly to reflect the new implementation (for instance, “Single-Agent Flow” might be described as an autonomous agent run with tools, and “Multi-Agent Supervisor Flow” might note multiple specialists collaboration). The final analysis heading for multi-agent is currently “Supervisor Narrative”[36]; this suggests the UI treats the supervisor’s final output distinctly. We’ll keep these nomenclatures, updating only if needed to better reflect the underlying process (e.g., if we call the multi-agent flow something like “Supervisor Orchestrated Flow” in documentation, we might mirror that).
    Agent run evidence: There is an agentEvidence badge in LiveArtifacts that shows if the answer was produced by an agent and how many turns, etc.[37]. After the refactor, for single-agent and multi-agent modes, we will always have an agent run, so this badge (“Agent Verified · X turns”) should consistently appear. We’ll ensure it’s correctly set based on the Agent SDK output – likely using the total number of reasoning turns or tool calls. If the agent falls back or is disabled (there are statuses for that in the code)[38], we should also handle those (for example, if the agent encountered an error and a fallback answer was given, the UI should indicate “Agent Fallback”). These cases should be rare once the system is stable, but the UI hooks are there and will be kept up to date with the new agent statuses.
    Preserve user experience of step-by-step breakdown: In summary, the front-end changes will maintain the current level of detail in explaining the workflow to the user. Users will still see that an input query led to a sequence of steps – data fetched, charts drawn, insights generated – but now it will be clearly driven by an AI agent’s decisions rather than a fixed sequence. The ProcessPanel and LiveArtifacts will function as a “window into the agent’s mind,” showing each tool usage and thought in order. Importantly, for direct mode queries, the UI will behave exactly as it does today (since that mode remains unchanged and yields the existing event types and process visualization). We will thoroughly test the UI with all three modes (direct, single-agent, multi-agent) to ensure the ProcessPanel and artifact views adjust appropriately based on the presence or absence of agent-specific events. The goal is that after refactoring, the UI presents a unified, transparent process timeline for agent-powered queries without confusing gaps or legacy artifacts, addressing the current telemetry mismatches where fresh runs lacked certain badges[27].
    
    
    Legacy Code Deletion Plan
    Once the new agent-based implementation is fully functional and verified, we will proceed with a phased cleanup of legacy code. The deletions will remove any dead code and simplify the codebase to only support the new architecture (plus the direct mode). Key parts of this cleanup include:
    Remove the old AnalyticsWorkflow and helpers: The AnalyticsWorkflow class in analytics_agent.py (along with its _build_* methods for crafting SQL, charts, etc.) will be retired entirely. These methods were part of the earlier deterministic implementation and are no longer called in the new pipeline[20][21]. We will verify that all necessary logic (e.g., specific SQL patterns for certain intents) have been transferred either to our YAML templates or new planner logic. Then, this file can be deleted or drastically slimmed down. This also avoids confusion from having two different pathways for generating outputs in the repository.
    Eliminate duplicated planner controllers: With single-agent and multi-agent flows now handled by the Agent SDK, the bespoke controller classes (SingleAgentController, MultiAgentFlow) and any related classes like PlannerSequencer used exclusively by them can be removed or merged into the unified flow. For instance, if SingleAgentController.events() simply calls into PlannerExecutorFlow (post-refactor), we don’t need a separate class at all – calls to instantiate a SingleAgentController could be replaced with a factory method that invokes the agent-enabled PlannerExecutor. We’ll remove intermediate layers like PlannerOrchestratorAdapter or others if they were only supporting the old controllers. The architecture principle is not to keep any vestigial “two-track” code: after this, aside from some conditional in the flow entrypoint for direct vs agent mode, everything funnels through the AgentRuntime. Thus, classes and functions that solely existed to support the old agent controllers can go.
    Delete regression-only pipeline code: During development, we maintained some legacy pipeline code for regression testing (to compare outputs). For example, the sequential pipeline might have been preserved in code (behind a flag or separate call) so tests could assert that the agent’s answer matched the old answer. Once we are confident in the new implementation, we will remove these old execution paths and any tests relying on them. This includes any special testing hooks that run the deterministic flow when in agent mode, or any stored baseline outputs from the legacy system. Going forward, tests will validate outputs against expected results (which may themselves be produced by the new system or taken from known correct answers), rather than against a parallel legacy run. The “planner-executor” code outside of direct mode will no longer exist to be invoked. As noted in the architecture notes, legacy sequential pipelines will be removed from runtime entirely[24], meaning in production no user can trigger them. We will mirror that in our code by excising them.
    Clean up configuration toggles: We will remove now-unused feature flags and settings related to old modes. Flags like ANALYTICS_FLOW_MODE=planner-executor vs single-agent and AGENTIC_REVISIONS_ENABLED served during the transition. After a successful rollout, we can simplify to assume agent mode is always on (with perhaps an override only for the direct mode case). The LaunchDarkly toggles or environment variables used to turn the new system on/off can be retired from the code (to avoid accidentally toggling back to an unsupported path). We’ll document this in our config files, and update any deployment scripts to remove references to toggling back. Essentially, once legacy code is gone, the flags controlling them go too.
    Deprecate outdated utility modules: Some supporting modules may no longer be needed. For example, if we had flows/planner/revision.py for computing revision targets in the old system, that logic might now live inside the agent’s decision-making. If so, we can delete revision.py or at least those parts of it not used elsewhere. We’ll perform a sweep of the codebase for any functions that are now unused (e.g., anything that was only called by deleted controllers). These will be removed to prevent bloat. Also, any duplicated logic between the old and new implementations will be reconciled and the duplicate dropped.
    Testing the deletion phase: Before fully committing removals, we will run the full test suite and ensure all references to legacy components are gone or updated. The deletion should happen after the new system has soaked in production (or at least in staging) and proven stable – likely we will keep the old code around but dormant behind flags for one version iteration, then remove it. By following this plan, we ensure we don’t accidentally remove something still needed. The final state will reflect the new architecture as the only architecture for agentic analytics, simplifying future maintenance and onboarding (new developers won’t need to understand a deprecated pipeline that’s no longer in use).
    
    
    Telemetry + Testing Guidelines
    Unified Telemetry and Monitoring: A crucial part of this refactor is that telemetry events are standardized across fresh and revision runs. We will leverage the OpenAI Agent SDK’s streaming events (via the Runner.run_streamed callback) to emit our existing SSE messages through AgentsStreamBridge for every agent-run flow[2]. This means both single-agent and multi-agent sessions will produce events like tool_call_delta, tool_call_summary, agent_reasoning, etc., which the front-end and our monitoring systems can consume. We’ll verify that the content of these events includes all the fields our UI and analytics expect (tool names, timestamps, etc.). For instance, AgentsStreamBridge._emit_tool_call_delta() already formats tool arguments and partial outputs into SSE payloads[28], and similar methods handle reasoning and completion. We must ensure these methods are invoked for fresh runs now, not just revisions. We will also continue annotating each event with flow metadata (mode, parallel group, reuse flags) via apply_mode_metadata() so that logs and UIs display context consistently[39]. The alignment of telemetry means we can finally compare performance and behavior between fresh and revision flows apples-to-apples – the same counters and metrics will apply to both.
    We will update our Grafana dashboards and alerts to cover the unified agent telemetry. For example, metrics like agent_turn_error_count or agent_retry_rate (which were tracked only for multi-agent revision flows) will now also reflect fresh query runs[40]. We should audit any logging/telemetry code in core.telemetry or elsewhere that might have been hard-coded for revision flows and make it general. The architecture already notes that structured telemetry is emitted for all modes via a common path[41], so this should largely fall into place once the agent is always in use. We’ll test in staging that events like “agent_supervisor_started” and “agent_supervisor_summary” are emitted appropriately for multi-agent cases (these contain the list of specialists and are useful for analytics)[42][43].
    Session and outcome logging: The new system will log each agent run’s outcome (success, failure, fallback) through our existing channels. We must ensure that things like the final answer or any failure reason are clearly logged. The AgentsStreamBridge should catch exceptions and emit an error event if something goes wrong so that the frontend can display an error message and our logs catch the stacktrace. We’ll incorporate any additional logging from the Agent SDK (for example, if the Agent SDK provides a run ID or statistics about token usage, we might log that as well for later analysis).
    Testing strategy for functionality: We will undertake a comprehensive testing approach to validate that the refactor does not break existing functionality:
    Unit tests for new components: Write targeted tests for each new tool wrapper to ensure calling the tool yields expected results. For example, a test for the SQL Tool could set up a dummy query and verify that stream_sql_lane is invoked and the result is returned through the tool interface correctly. We’ll also test the dual agent configs: instantiate a FreshRunPlannerAgent and RevisionPlannerAgent in isolation and ensure they select the correct tools (e.g., fresh agent always calls all tools, revision agent maybe skips some if told to).
    Regression tests with baseline outputs: As an intermediate step, we will compare the agent path’s outputs to the legacy path’s outputs for identical inputs. For instance, we can take a representative set of queries and run them in FlowMode.DIRECT (legacy deterministic) and in the new FlowMode.SINGLE_AGENT, then diff the final answers and key artifacts. We expect them to match or be within acceptable variance. One concrete plan is to mirror an existing deterministic test: for example, if we have test_sql_lane_emits_receipts or a full pipeline test, we create a new test that runs the same scenario through the Agent SDK runner and then assert that the PipelineArtifacts or receipts produced are equivalent[44]. This gives us confidence that the refactor hasn’t altered the end results (except where intentionally improved).
    SSE event sequence tests: Adapt tests like test_agents_stream_bridge.py and other SSE verification tests to run in fresh mode as well. We likely already have tests for revision that check the presence of events like tool_call_delta, analysis_revision, etc. We will add similar tests for a fresh query in agent mode, ensuring that events like sql_ready still appear (likely via the tool events) and that an agent_supervisor_summary appears at the end of a multi-agent run listing all specialists. We will also validate that no extraneous or duplicate events appear. Essentially, the sequence of events for a given scenario should be deterministic and logical – tests can assert the order (e.g., that a tool_call_delta is followed by a tool_call_summary for the same tool, etc.).
    Performance and guardrail tests: Create tests to ensure the guardrail logic integrated into the agent works. For example, simulate a follow-up query that should trigger a “stock-only update” and confirm that the agent (via guardrail or logic) skips the heavy steps and that the resulting events show a reused SQL and chart with only analysis refreshed. We might use a stub or mock for the follow-up classifier if needed, or better, structure the agent prompt such that it naturally does the right thing. Additionally, test that the latency guardrail (if a web search takes too long, for instance) triggers the same way as before – possibly by injecting delays in a tool and seeing if our latency_guardrail event is emitted.
    Direct mode regression tests: Since direct mode code remains, we will keep its tests around to ensure we haven’t inadvertently broken it while refactoring nearby code. All direct mode tests (which often validate exact output structures and caching behavior) must continue to pass. They will serve as a canary that our shim logic in PlannerExecutorFlow properly leaves direct sessions unaltered.
    End-to-end and UI tests: We should run Playwright or Cypress (if available) tests on the front-end to ensure that a full round-trip query yields the correct UI updates. For example, an automated test could input a query, wait for the ProcessPanel to show final results, and then check that the expected elements (chart, analysis text, etc.) are present and labeled with the right mode. If we have snapshots or logs of what the UI looked like in various scenarios pre-refactor, we can compare them to post-refactor (bearing in mind some intentional changes like additional “Agent” badges). Any existing frontend Jest tests for components like LiveArtifacts should be updated with new prop expectations if needed (e.g., if specialistCards prop is now always populated where it was sometimes empty).
    Parallel runs and stress tests: Because the Agent SDK introduces a different execution model (especially for multi-agent with potentially concurrent tool calls), we’ll do stress testing to ensure our system handles it. This includes running multiple sessions in parallel to see that our Redis cache and session stores behave (the architecture’s cache circuit-breakers should help)[45]. We’ll monitor for race conditions or memory leaks in the new flow. Automated tests could spawn, say, 10 concurrent agent sessions and assert that all complete and produce correct results, which helps flush out any event-loop or concurrency issues in our Python async code.
    Telemetry validation and future-proofing: We will expand our test coverage to include telemetry correctness. For instance, we could have a test that runs a multi-agent flow and then inspects the specialists list in the final summary event to ensure all expected specialists are listed. We might also parse the agents.event_bus or logs to confirm that every tool invoked has a corresponding receipt in the session snapshot. Furthermore, as we integrate GPT-5, we will keep an eye on compatibility (GPT-5 function calling might be stricter with tool definitions, etc.). We’ll follow OpenAI’s best practices (per their documentation and our internal gpt5-best-practices.md) to configure the agent (e.g., making sure we provide clear tool descriptions and test with the specific model to avoid runtime surprises)[12].
    In summary, testing will be thorough and multi-layered – from unit tests of new functions to full integration tests comparing old vs new behavior. Telemetry will be carefully monitored in staging: we will use the unified telemetry feed to run our evaluation pipeline (replaying agent logs, verifying no regression in key metrics like accuracy or latency). Only after tests and telemetry analyses show parity or improvements will we proceed to full production rollout.
    
    
    Tooling, Rollout, and Validation Strategy
    Incremental rollout with feature flags: We will not flip the entire system to the new approach in one go without safety nets. Instead, we’ll use our feature flag system (e.g., LaunchDarkly) and environment toggles to gradually route traffic to the new agent pipeline[46]. Initially, we can deploy the refactored code with the flag still defaulting to the legacy planner for fresh runs. In staging environments, we will turn the flag on to have all fresh and revision requests go through the Agent SDK, and closely monitor the outcomes. Once we are satisfied in staging, we can do a controlled production rollout: for example, enable the single-agent mode for a small percentage of sessions or for internal users first. Given the project timeline in docs (targeting week of Nov 10, 2025 for launch), we have likely already done a lot of this. In production, when ready, we toggle ANALYTICS_FLOW_MODE=single-agent (and ensure AGENTIC_REVISIONS_ENABLED=true) to send all new sessions to the unified agent flow[47][48]. The direct mode remains available as a separate demo or can be triggered by certain queries, but normal user queries would now use the agentic path by default.
    Pre-launch validation checklist: We will follow a rigorous pre-launch checklist (as outlined in our rollout plan documentation) to validate the system’s readiness[49]:
    Communication and training: Confirm that all stakeholders (engineering, support, SRE) are aware of the change. As noted, support macros/FAQ were updated to reflect the new agent behavior[50] – this ensures our support team knows how to troubleshoot or answer user questions about the new multi-step AI reasoning they’ll see.
    Cache warm-up: Since the new system might query different things or put different load on caches, ensure we prime the cache. The checklist mentions running a pre-warm script[51] – we likely have a script to pre-cache common tool responses or ensure the Agent’s prompt templates are loaded into memory.
    System monitoring set-up: Verify that dashboards for agent metrics (turns, errors, latency) are in place and that PagerDuty alerts for any spikes in errors or latency have been configured[40]. We specifically watch metrics like sse_delivery_latency to catch any slowdowns in streaming, and any increase in error rates now that more complexity is in play.
    Database/Redis backup: Take a snapshot of the database and Redis state before rollout[52]. This is important in case something goes wrong with how we store session states or agent metadata in cache – we could restore previous state if needed.
    Deployment and live testing: During the deployment window:
    Temporarily freeze new sessions on the old planner to avoid in-flight queries during the cut-over[48]. Then deploy the backend with the new code and flip the flag so that subsequent sessions initialize in agent mode. Also deploy the frontend update so that the UI can handle the new telemetry (the UI is backward compatible, but any new labels or changes should go out at the same time to avoid confusion).
    Perform a smoke test in production immediately after enabling the agent. The docs reference a script dump_agents_stream.py[53] which likely runs a representative query and dumps the entire SSE stream output. We will run this for a few queries to confirm that: the agent is producing all expected events, the final answers look correct, and no exceptions occurred. Archive these outputs as a record.
    Spot-check UI: open the live app, run a few queries in each mode (direct, single, multi) to visually confirm the ProcessPanel and LiveArtifacts look as intended with the new data.
    Monitor health checks and system endpoints to ensure the service is running normally after deployment (e.g., hit the /analytics/_status endpoint and ensure it returns healthy)[53].
    Post-rollout monitoring and fallback plan: Once the new system is live for all users, we will intensively monitor for at least 24 hours:
    Check logs for any Agent errors or anomalies – e.g., any agent_turn_error entries where the agent failed to complete a step or any tool invocation errors (perhaps the Agent tried something unexpected). Our plan mentions reviewing logs for multi-agent retries &gt; 2 (which could indicate a specialist failing and the supervisor retrying) and SSE disconnects[54]. If these are within normal range or baseline, we proceed; if they spike, investigate quickly.
    Verify that the cache service is storing agent run metadata correctly (session IDs, etc.)[54]. We added functionality for caching per-session agent metadata (like run IDs, retry counts) in the architecture, so we want to ensure that’s working and not growing uncontrollably[45].
    Collect initial performance metrics: Is the average latency per query improved or at least not worse? Is the system handling as many QPS as before? The expectation per project goals is improved latency in some areas (the roadmap targeted ~60% better clarification latency)[55]. We will gather data on actual improvements and any regressions.
    Solicit any user feedback or issues via support within that first day, and be prepared to respond.
    If at any point we discover a severe problem (e.g., agent answers are consistently wrong or some crucial feature broke), we have a rollback strategy ready[56]. This includes: - Using the feature flag to immediately route new sessions back to the deterministic planner (planner-executor mode)[57]. - Redeploying the previous stable version of backend (and frontend if needed) that had the old code path[57]. - Clearing or invalidating any cached agent-specific data (the checklist mentions a script to purge agent cache)[58] to avoid confusing the old code with new artifacts. - Notifying stakeholders and doing a post-mortem if a rollback happens[59].
    Validation and future-proofing: Assuming the rollout is successful, we will do a follow-up:
    Mark the project status as “Production” on the roadmap and document the outcomes (the rollout checklist noted updating the roadmap doc and publishing a summary report)[60]. We’ll include metrics achieved, any incidents, and confirmation that the new architecture meets our goals.
    Plan for any backlog tasks that we deferred. For example, once the supervisor+tools model is stable, we might revisit the idea of a Planner agent that dynamically orders tasks (as mentioned in the architecture vision)[7]. We’ll only pursue this after validating that the current approach is solid and maintainable. Similarly, we may explore enabling the more complex “Supervisor handoff” pattern in the Agent SDK in the future, which would require UI changes for nested timelines – but this is optional and will be considered separately[61].
    Continue to incorporate OpenAI’s latest best practices. The OpenAI Agent SDK may evolve, so we’ll keep an eye on any updates, especially around multi-agent orchestration. We have aligned our design with known patterns (manager agent with tools), which should be stable. Any future improvements (like better error handling or new features in the SDK) can be adopted to further harden the system.
    Testing and telemetry ongoing: We will keep our expanded test suite as a permanent part of the project. The tests for agent flows will guard against regression as we modify the system in the future. Telemetry dashboards will remain in use to catch any drift in performance or errors over time.
    By executing this rollout carefully and with ample validation at each step, we ensure that the transition to an Agent SDK-based architecture is smooth and does not disrupt users. We preserve the option to fall back if needed, but aim to fully deprecate the old system once confidence is earned. The end result will be a modernized analytics pipeline that is easier to maintain, aligned with the agentic vision in our roadmap, and ready for future enhancements with minimal technical debt[62].
